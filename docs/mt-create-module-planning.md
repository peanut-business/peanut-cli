# MT create selection and native composition boundary

This is a CLI selection contract, not a completed first-install workflow. The public immutable module RC.1 remains an upstream verified input; this change does not publish, retag or repeat its qualification. It does not create a real application or operate a database.

## One product composition source

The selected scaffold template owns `server/config/module_composition.json`, declared in its create inventory and covered by the existing template archive/file digests. CLI reads those exact bytes before rendering. No private repository or Code source checkout is a runtime/package dependency. No separate CLI membership list is shipped.

The format is the existing S3 `peanut.application-module-composition.v1`: `schema_version: 1`, independent SemVer `version`, nonempty `mandatory` and possibly empty `default` arrays. Each entry is an official Module key, and categories are disjoint. Code must add an explicit `optional` array (empty is valid) to complete the three-way product classification. Until then CLI reports `CODE_OPTIONAL_MODULE_CLASSIFICATION_REQUIRED`; absent optional does not mean every other published Module is approved. The manifest may be an application-owned config default, but planning uses its template-bound original bytes and records their SHA.

`standard` selects mandatory + default; `minimal` selects mandatory. Explicit `--modules key,key` can add only declared optional roots. These are root selection rules, not dependency resolution. Mandatory Modules can also require otherwise unselected Modules, including those outside these root categories; Code owns their full graph and compatibility admission.

## Fixed source snapshot

`--module-release` always fixes one exact module Release tag independently of the template ref/channel. Online selection reuses the existing official repository/API identity and independent asset digest checks. Offline selection requires an absolute `--module-index` and independently reviewed `--module-index-sha256`; it verifies the same v1 schema and tag binding. It records local digest-pinned provenance, without inventing publication verification. Offline stable Release channel verification is unavailable, so it requires explicit `--module-channel prerelease`.

Both paths produce `peanut.create-module-selection.v1` with the template version/source/archive SHA, preset version/SHA, repository/tag/commit/index SHA, sorted roots, exact selected index entries and the full snapshot catalog. Missing roots, unsupported Edition and disallowed root prereleases are reported as blockers. The catalog preserves dependency declarations for a future native consumer; it is not an admitted graph. This command does not download or verify any Module TAR. It does not choose another snapshot or retry candidate versions.

## Required Code contract before create may continue

These are required semantics, not claimed command names. Code must own and document a public machine-readable entry and ship it in the relevant template/tooling:

1. Input: MT Edition, selected roots/preset identity, one pinned index identity, verified candidate TAR paths with exact keys/versions/SHA, and the current application/lock state (empty for fresh APP). It must work before business Modules, application service providers and the database are available. CLI can download/verify candidates using its existing official Module transport when this interface is ready.
2. Planning: use the existing Composer constraints and native `PackageCheck`, archive/lock/host/Core checks, and native dependency ordering to derive the entire transitive closure. Report all missing/incompatible dependencies and cycles together, exact chosen versions/digests, additions/upgrades/retained/uninstalled/disabled state, affected files/locks, migration identities and backup needs. Do not require per-module failed installations to discover the graph. Retain compatible higher installed versions and reject downgrades or same-version content changes. CLI must not parse/evaluate Composer ranges or build an independent solver.
3. Source preparation: expose a supported pre-bootstrap whole-plan stage/adopt path using the existing native source/lock transaction and recovery mechanism. It may promote verified sources and locks only after whole-graph admission. It must not register installed state, write database schema/migration state, enable tenant Modules, grant RBAC or claim runtime activation. An existing API is sufficient if Code confirms these semantics; a new parallel installer is unnecessary.
4. Response: stable schema version, plan/operation identity, exact selected closure and sources, native diagnostics on nonzero exit, precise source/lock write set, completed writes and a native recovery handle on failure. Unknown/running operations are reconciled through that handle, never replayed blindly.
5. Bootstrap: after source preparation and database readiness, the existing first installer performs initialization/migrations and records actual installed state. CLI create must never invoke DB-changing `module:install-package` before that point. Later native install/upgrade/reconcile remains an explicit application lifecycle operation.

Until Code documents and delivers this contract, `create --plan` always returns `blocked` with `CODE_NATIVE_COMPOSITION_PLAN_REQUIRED` and exits 1. It writes no target, calls no PHP/native bridge and performs no dependency or database operation. Explicit composition arguments require `--plan`; ordinary create retains its existing template source-generation behavior and makes no new external composition or first-install guarantee. A composition manifest by itself does not declare whether a template already bundles its required sources. Real MT first installation, activation, frontend compilation and lifecycle qualification are NOT_RUN by this CLI change; ST development/testing is out of scope.
